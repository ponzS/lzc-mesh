# 跨平台键鼠交接修复验证（进行中）

Linux 支持范围暂时仅为 Omarchy（Hyprland）。本文记录 v0.2.2 的交接修复及验证边界；既有 v0.2.1 标签不包含本轮修复，不移动旧标签。

## 用户确认

用户在最终 Windows 捕获修复安装后手动复测，确认本次 Windows ↔ Mac 问题已恢复正常，并授权发布 v0.2.2。此确认针对报告的实体鼠标跨屏异常，不等同于六方向完整实体输入或蓝牙硬件验收。

## 已实现

- 已批准的当前接收端可因本机真实输入收回控制；接管请求绑定控制 ID，中枢拒绝第三方、跨账号及过期请求。
- 三端控制与接收角色互斥，原生回调按会话过滤，接管后旧回调不能重新注入；结束的原生会话不重新激活。
- Mac 接收前解除捕获、恢复本应用隐藏的光标并做一次入口位置恢复；未改位移增益或滚动算法。
- Windows 每次成为控制端时在专用钩子线程重建键盘钩子；本机接管先释放远程状态，再交付触发输入。有界缓冲超限时安全释放，不记录键码或输入字符。
- Omarchy 只在受控期间读取已有权限的物理 evdev 节点，不抢占设备或修改权限；缺少权限时告警。键码和按钮使用整数 JSON，核心兼容合法整值浮点数并拒绝无效编号。

## 已获得的证据

- 中枢单元回归：31 项通过。
- 共享传输核心：23 项通过，包含真实回环 QUIC、六个平台方向的键鼠与反向路由、接管及旧会话隔离。
- 独立真实中枢协议组件：六个方向的接管、释放、反向键盘、过期请求和账号隔离通过。
- 原有真实中枢／浏览器回归：设备信任 5 项、休眠生命周期 4 项通过。
- 三端及 LPK 构建通过；原生回调门控、实体活动分类、Omarchy 全部键码及按钮整数序列化测试通过。
- 已安装的 Mac→Windows、Windows→Mac 严格局域网实测通过：F6、Shift+F6、点击、12 像素拖拽、右键、滚动、紧急收回；Mac 接收光标可见。

上述桌面测试使用专用窗口和合成 OS 输入，不等同于物理键鼠或完整硬件验收；Windows 边缘申请由测试消息触发，实际实体边缘及三端实体接管还需验收。Omarchy 当前未建立局域网直连，不把中转说成直连。

## 入口稳定性补充排查

- 用户报告 Windows 向下进入 Mac 时偶发错误位置或不可见；尚未宣布该用户症状彻底解决。
- 修复前增加 Mac／Windows 交替 6 轮桌面观察：覆盖共边不同水平位置、可见入口、24 像素移动和真实跨边返回路径，均通过。输入仍为合成 OS 事件，不是实体边缘／实体接管认证。证据：`.run-ac/cursor-stability-r1/`。
- 新增确定性回归复现了发送端串扰：旧捕获中迟到的移动可作用于新同向授权并触发错误返回。三端发送输入现绑定产生它的捕获会话，核心丢弃失效／错配的移动、键盘、按钮、滚动和释放；Windows 迟到的捕获故障还须匹配捕获代次。原有位移和滚动算法未改。
- 上述发送隔离修复已构建并安装到三端，批准指纹、配置和当前共边布局均保留。对应组件回归修复前失败、修复后通过；Windows 实际队列的会话序列化测试通过。
- 修复后的重复桌面执行因专用窗口失焦而中止（`.run-ac/cursor-stability-r2/`），随后观察到非测试所有的 Windows→Mac 会话，未收回或暂停它。后续只读确认 Mac 也已锁屏；该轮不能记为功能通过或复现了用户的原始故障。
- 已关闭专用观察器，未对非测试会话注入。账号设置保持原值，没有移动布局或改变系统锁屏策略。观察器补充远端心跳检查、异步焦点等待、暂停期间预检与中心停放、动态锁屏检查；Mac 观察器避免自身 App Nap，但不阻止系统休眠或锁屏。补充工具已编译，尚待下一次解锁／空闲窗口实测。

## Windows 实体鼠标固定左下角：只读现场证据与待装修复

- 用户再次报告使用 Windows 实体鼠标时 Mac 光标固定左下角。只读查询确认当前所有者为 Windows→Mac；Mac 未锁屏、未启用安全输入，入口日志在顶部，但后续位置反复为 `(0.000, 0.999)`，实际系统光标约为 `(0,1110)`。
- 独立的隐形只读鼠标诊断进程记录 Windows 光标仍在出屏处 `(728,1439)`，而不是代码假定的捕获中心；屏幕为 2560×1440、DPI 96，鼠标裁剪范围覆盖整个桌面。此时继续用中心 `(1280,720)` 相减会产生约 `(-552,+719)` 的错误位移，与 Mac 持续钳在左下角一致。
- 两次 30 秒诊断窗口内未收到新的实体移动，故不把静态采样说成已采到完整实体鼠标事件轨迹。诊断不注入输入、不移动或裁剪光标、不激活窗口、不读取键盘；进程已退出，启动任务已移除，未收回用户会话。
- Windows 修复已安装：入口定位改为本应用专用标记的绝对输入，钩子确认当前定位代次后才转发；迟到的旧定位及旧接收移动不能挪动新控制端；超时或定位未落实时安全结束捕获。相对移动以实际事件前光标为基准，保留原 DPI 增益；两类钩子在进入控制角色时均重新就绪，发送入队还须匹配捕获代次。Mac／Omarchy 的位移和滚动代码未改。
- 生产捕获门控、旧代次拒绝、错误基准等价类、19,320 个像素定位及既有队列／小数滚动回归通过，共享核心 23 项通过；Windows 完整构建通过。
- 用户随后明确授权直接维护更新。确认仍为同一已报告会话后暂停账号接力，再进行 Windows 单端维护；不是擅自收回未知替换会话。最终安装哈希为 `df2205a18e6d900830680ab3657d65e7430ef38b0b9839b80d8c4cbb41dceea1`，配置字节保留，原批准指纹和身份不变。
- 新增 `windows-capture-os.cpp` 在真实 Windows 专用窗口链接未改写的生产 `input.cpp`，仅替代传输及日志，不向任何设备发送输入。它在外部维护守卫确认暂停／空闲后临时停止并恢复客户端，以避免两个副本的全局钩子互相影响。执行中发现该输入栈截断标记高 32 位，旧的 64 位定位标记无法确认；已改用独立 32 位标记，并继续用完整捕获代次保护队列与定时器。
- 上述 OS 组件修复后 3 轮通过：从 Windows 底部不同位置准确定位 `(1280,720)`，正反 `(2,3)` 小位移及会话绑定正确，旧定位和旧接收移动未改变新控制端。证据：`.run-ac/windows-park-os-r6/`。这是生产源代码在真实 OS 上的合成鼠标组件验证，不是经过真实中枢的跨屏验收，也不是实体鼠标认证。
- 最终构建已重新安装，三端在线且批准状态不变；维护暂停已解除，原账号设置、当前布局、独立开关均保留，确认 `active:null`。临时测试窗口、进程和任务已清理。Mac 在维护期间锁屏，未向其注入输入或尝试解锁；完整跨屏及实体鼠标复验仍待正常解锁后完成。

- 布局不共边时不能跨屏；测试临时贴齐后恢复原布局和账号设置，未擅自永久调整布局。
